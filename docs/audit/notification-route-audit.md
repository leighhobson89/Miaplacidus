# Notification route audit: space, weather, saves, and battles

**Audit date:** 5 October 2026  
**Purpose:** map Cosmic Forge notification categories to the remake's typed events, current notification routes, localization, and focused acceptance coverage. This is a static source audit; recommendations below are proposed implementation contracts, not claims that those routes already exist.

## Implementation follow-up

The event routes described below have now been implemented in `src/app/spaceEventNotifications.ts` and `src/i18n/spaceNotificationMessages.ts`. `withGameAudio` forwards accepted dispatch events once, including timer-generated events from `clock.advance` and accepted batch results; `App.tsx` connects those events to the existing notification stack. Starship travel uses `starShip`, rocket travel uses `rocket`, hazardous weather uses `weather`, and battle completion uses `battle`. Weather notifications fire when conditions enter rain, heavy rain, or volcanic hazard; repeated conditions and clear/cloudy cycles stay silent. Battle rounds and shortened starship travel stay silent. Space notification copy has entries for all six supported locales. Unit coverage passes; the rendered starship-launch and battle-outcome assertions are staged for the serialized browser run. Local save feedback remains at the UI boundary, with no cloud-save claims.

## Current remake path

The remake renders notices through `src/app/NotificationStack.tsx`; `src/app/notificationScheduler.ts` limits visible categories to four, queues ordinary categories in order, and allows the existing `storage`, `debug`, and `achievement` multi-card groups. `SettingsPane` can disable the region. The current routed notices are:

| Remake event / source | Current route | Locale source |
|---|---|---|
| Economy technology learned (detected by the `App.tsx` state-diff effect) | `tech`, info | `technologyNotificationMessages.ts` |
| Cosmic Rip technology learned (state-diff effect) | `cosmicRip`, info | `cosmicRipMessages.ts` |
| `economy.fusion.completed` | `fuse` | `economyMessages.ts` |

At the time of this audit, `EngineResult.events` carried typed `SpaceEvent`s but `App.tsx` did not route them to notifications. The implementation follow-up above routes each emitted event once, including events produced by timer advancement; state-diffing the full game state could miss repeated events and duplicate notices after save replacement. Save outcomes remain outside the engine and are routed from the persistence/UI result.

## Implementation contract

1. Add one typed notification adapter for `EngineResult.events`; handle space events alongside existing routes without inferring events from UI state. Ensure the dispatch/tick boundary exposes timer-completion results and that each event is consumed once.
2. Map only player-visible milestones: starship/rocket launch and arrival, a newly hazardous weather condition (plus an explicit relief policy), and battle completion. Ignore progress ticks and routine clear/cloudy changes.
3. Keep repository outcomes in the persistence/UI layer. Use local-save language and current save error codes. Source cloud notifications are not parity requirements for local storage.
4. Add or reuse message keys in each supported locale (`en`, `es`, `pt`, `de`, `it`, `fr`). Keep placeholders named and stable (`{system}`, `{rocket}`, `{asteroid}`, where used); unit tests should check all six catalogues have matching keys and interpolation.
5. Preserve the notification setting and scheduler semantics. Test classification, type, localized copy, exactly-once delivery, and no notice for events deliberately excluded above.
